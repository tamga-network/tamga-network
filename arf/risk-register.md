# Risk Register

Official English translation of the Turkish source text; in case of conflict the Turkish text prevails.

This document shows, for every risk and threat in the EU wallet risk register, Tamga's measure and its status; it is for
regulators, states, auditors and participants.

> **Self-assessment.** This register is Tamga's own assessment; it is not an independent audit, a conformity assessment or a
> certificate. "Met" is used only for measures backed by a binding rule and present in the reference implementation.

**When to read it.** First the security section of the main document ([[FW-ARF-0001]] §7) and the risk approach of the Trust
Framework ([[FW-TF-0001]] §1.5). The rules behind the measures are in the Tamga Rulebook ([[FW-RB-0001]]) and in the cited
specifications and decisions.

## 1. Source and method

The EU collects the risks that every wallet architecture must address in a common risk register: Implementing Regulation (EU)
2024/2981, Annex I (Annex 6 of the EU ARF). It has four sections: high-level risks (R1–R14), system-related risks (SR1–SR3),
technical threats (TT1–TT5 with subcategories) and direct threat scenarios (TR1–TR133). This document follows the same
skeleton; codes and titles are those of the regulation.

Tamga Network does not operate a wallet ([[ADR-0042]]); for wallet-side rows the measure is the set of rules the Tamga Rulebook
places on listed [[t:wallet-provider|wallet providers]] (RB-WP) and the open-source Tamga wallet core.

| Column           | Meaning                                                                                                                                                                                                                                                                |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Who              | The role responsible for the measure: operator (the network's provisional operator), identity service (Tamga's provisional identity credential service; not a PID), issuer, verifier, wallet provider                                                                  |
| Measure in Tamga | A short description and the source of the rule (`DOC-ID/CODE` or a Tamga Rulebook rule code)                                                                                                                                                                           |
| Status           | **Met**: binding rule and present in the reference implementation · **Partly**: a measure exists but is incomplete, not yet verified on phones or not certified · **Open**: no measure · **Not applicable**: the function the threat relies on does not exist in Tamga |

Threats about the PID were read as applying to Tamga's provisional identity credential (Tamga issues no PID —
[[SPEC-TRUST-0001]]/TL8).

## 3. High-level risks

| Code | Risk                                               | Main measures in Tamga                                                                                                                                                                                                     | Status |
| ---- | -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| R1   | Creation or use of an existing electronic identity | The identity credential is issued only after licensed remote identity proofing and the person's final confirmation in the wallet that started the flow; copies are bound to keys the wallet proves. No independent audit.  | Partly |
| R2   | Creation or use of a fake electronic identity      | Tamga issues no PID; the identity service is registered in the trusted list with a credential-type authorisation; an unauthorised type is rejected in verification. The list signature rests with a single operator today. | Partly |
| R3   | Creation or use of fake attributes                 | Every credential is signed, the signer is in the trusted list and the type authorisation cannot be skipped; holder binding is mandatory. Fabrication inside an institution is under the institution's own controls.        | Partly |
| R4   | Identity theft                                     | Keys in the device's secure area, every presentation with user verification; unit revocation without the phone. No certified secure hardware (W3).                                                                         | Partly |
| R5   | Data theft                                         | No personal data in shared records; responses are encrypted; the log stays on the device and leaves only in the person's encrypted export; no wallet backup.                                                               | Partly |
| R6   | Data disclosure                                    | Selective disclosure, field-by-field consent, scope check, mandatory registration certificate; linkage remains possible if credentials of the same issuer are combined (FW-ARF-0001 §7.4 L3).                              | Partly |
| R7   | Data manipulation                                  | Credentials are signed; the acceptance decision is in the verifier's own pipeline. The wallet log has no integrity protection.                                                                                             | Partly |
| R8   | Data loss                                          | There is deliberately no wallet backup; credentials are issued again on a new device, the log moves only with the migration file.                                                                                          | Partly |
| R9   | Unauthorised transaction                           | Signed request, registration certificate, single-use nonce, user verification for every presentation; phishing cannot be ruled out entirely.                                                                               | Partly |
| R10  | Transaction manipulation                           | Request, response and credential are signed and encrypted; open: proof that the credentials of a multi-credential presentation belong to the same person (TR86).                                                           | Partly |
| R11  | Repudiation                                        | KB-JWT and the device signature evidence the presentation; the verifier's audit record is kept for rejections too. The log is lost if the device fails.                                                                    | Partly |
| R12  | Transaction data disclosure                        | The presentation log stays on the device; verifier results and logs carry no field values and no status-list position; IP addresses are not logged.                                                                        | Partly |
| R13  | Service disruption                                 | A stale or unreachable trust source yields "indeterminate", never acceptance; status lists are static and fetched in bulk; no load or outage testing yet.                                                                  | Partly |
| R14  | Surveillance                                       | No global identifier; a copy per verifier, a pseudonym per site, zero-knowledge proofs; status lists at a fixed interval and in bulk.                                                                                      | Partly |

## 4. System-related risks

Under the regulation these risks are the system-level result of several threats; they are not mapped to threat scenarios.

| Code | Risk                   | Main measures in Tamga                                                                                                                                                                                                                                               | Status |
| ---- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| SR1  | Wholesale surveillance | No central service sees transactions: trusted lists and status lists are fetched in bulk, the presentation log stays on the device, shared records hold no personal data. Against colluding verifiers, zero-knowledge proofs exist only for the identity credential. | Partly |
| SR2  | Reputational damage    | Incident notification deadlines, a public change log and a quarterly transparency report; no independent audit or certification.                                                                                                                                     | Partly |
| SR3  | Legal non-compliance   | The network is not bound by EU law but follows the EU model; personal-data rules are protected by binding rules; the legal review of the framework is due before the pilot.                                                                                          | Partly |

## 7. Open topics

1. **Same person in a multi-credential presentation** (TR20, TR43, TR86): the verifier checks the holder binding of each
   credential in the same response separately; there is no cryptographic link showing that the credentials belong to the same
   wallet unit. The topic is under discussion in the EU as well.
2. **Integrity of the wallet log** (TR38, TR49, TR132): the log stays on the device but is not protected against modification
   or omission.
3. **Certification and independent audit**: there is no certified secure hardware (W3), no independent code audit and no
   penetration test; that is why most wallet-side measures are "Partly".
4. **Single operator** (TR4, TR17, TR78): the list signature rests with a single operator; the key ceremony and hardware
   security module are pending ([[FW-ARF-0001]] §7.4 L1).
